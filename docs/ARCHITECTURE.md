# Architecture

## Principles
1. **Simple over clever.** Plain functions, Server Components and Server Actions. No state
   libraries, no ORMs, no API layer unless something external needs it.
2. **Feature folders.** Everything about a domain lives together.
3. **The database protects data.** Row Level Security is the real authorization layer;
   UI checks are just UX.

## Folder structure

```text
src/
├── app/                      # Routes only (thin pages, layouts, route handlers)
│   ├── (marketing)/          # PUBLIC, INDEXED — paidlyo.com (header/footer layout)
│   │   ├── page.tsx          # landing  /
│   │   ├── features/[slug]/  # /features, /features/time-tracking ...
│   │   ├── pricing/
│   │   ├── blog/[slug]/      # /blog, /blog/how-to-invoice-clients ...
│   │   ├── alternatives/[slug]/  # /alternatives/harvest (later: programmatic SEO)
│   │   └── legal/            # privacy, terms
│   ├── (auth)/               # login, signup, reset — noindex
│   ├── app/                  # PRIVATE, NOINDEX — dashboard at /app/* (sidebar layout)
│   │   ├── page.tsx          # /app (dashboard home)
│   │   ├── time/
│   │   ├── clients/
│   │   ├── invoices/
│   │   └── ...
│   ├── i/[token]/            # client invoice page (no login) — noindex, never in sitemap
│   ├── api/webhooks/stripe/  # Stripe webhook route handler
│   ├── sitemap.ts            # marketing URLs only
│   └── robots.ts             # disallow /app, /i, /api, auth pages
├── components/
│   ├── ui/                   # shadcn components (generated; edit sparingly)
│   └── app-shell/            # /app sidebar nav, mobile nav, logo
├── content/                  # marketing content data (blog posts, feature pages, alternatives)
├── features/<domain>/
│   ├── components/           # UI specific to the domain
│   ├── actions.ts            # "use server" mutations (validate -> auth -> DB -> revalidate)
│   ├── queries.ts            # read functions used by Server Components
│   ├── schemas.ts            # Zod schemas (shared by forms and actions)
│   └── types.ts
├── hooks/                    # shared client hooks (only when truly shared)
├── lib/                      # framework glue: supabase clients, stripe, money, utils
├── types/database.ts         # generated by `npm run db:types` — never edit by hand
└── proxy.ts                  # refreshes Supabase session, redirects signed-out users
supabase/
├── config.toml
└── migrations/               # SQL migrations — the source of truth for the schema
tests/                        # Vitest tests
```

There is no separate `services/` or `utils/` folder: domain logic goes in the feature,
shared helpers go in `lib/`.

## Data flow

**Read:** `page.tsx` (Server Component) → `features/x/queries.ts` → Supabase server client (RLS).

**Write:** form → Server Action in `features/x/actions.ts`:
1. Parse input with the Zod schema.
2. Get the user (`supabase.auth.getUser()`); fail if missing.
3. Query/mutate through the RLS-protected server client.
4. `revalidatePath(...)` and return `{ ok: true } | { ok: false, error }`.

Actions return typed results; they do not throw for expected errors (validation, not found).

## Supabase clients (`src/lib/supabase/`)
| File        | Where                                   | Key            | RLS     |
|-------------|-----------------------------------------|----------------|---------|
| `client.ts` | Client Components                       | publishable    | yes     |
| `server.ts` | Server Components, Actions, Route Handl.| publishable    | yes     |
| `admin.ts`  | Stripe webhooks / trusted jobs only     | secret         | **bypassed** |

## Multi-tenancy
- Every business row has `organization_id`.
- A user belongs to orgs via `organization_members` (role: owner/admin/member).
- RLS policy pattern: row visible if `organization_id` is in the user's memberships
  (via a `security definer` helper function `is_org_member(org_id)`).

## Stripe: two separate uses
1. **SaaS subscription:** our customers pay us (Stripe Billing + Checkout + Customer Portal).
2. **Invoice payments:** *their* clients pay *their* invoices (Stripe Connect, so money goes
   to the user's own Stripe account). See open decision in PROGRESS.md.

Both go through one webhook route; events are verified with `STRIPE_WEBHOOK_SECRET`
and must be idempotent (store the Stripe event/payment id).

## Invoice PDFs
Start with a print-optimised invoice page (`@media print`) → browser "Save as PDF".
No PDF library until there is a real need (e.g. attaching PDFs to emails).

## Public site vs app (SEO)
One Next.js project, one domain: **paidlyo.com**.

| Area | Routes | Indexed | Rendering |
|---|---|---|---|
| Marketing site | `/`, `/features/*`, `/pricing`, `/blog/*`, `/alternatives/*`, `/legal/*` | **yes** | Static (SSG), `revalidate` for content updates |
| Auth | `/login`, `/signup`, `/reset-password` | no | Dynamic |
| Dashboard | `/app/*` | no | Dynamic, behind auth (`proxy.ts`) |
| Client invoice | `/i/[token]` | no | Dynamic |

Rules for every public page:
- Server Component, statically generated; no auth/cookie reads (they make the page dynamic).
- `generateMetadata`/`metadata`: unique title + description, canonical URL, Open Graph.
  `metadataBase` = `NEXT_PUBLIC_APP_URL` in the root layout.
- One `<h1>`, semantic headings, descriptive link text, `next/image` with `alt`.
- JSON-LD structured data where relevant: `Organization` + `WebSite` (layout),
  `SoftwareApplication` (landing/pricing), `BlogPosting` + `BreadcrumbList` (articles), `FAQPage`.
- Listed in `sitemap.ts`; linked from navigation, footer or related content (no orphan pages).
- Minimal client JS: interactive bits (mobile menu, pricing toggle) are small client components.
- Social share images via `opengraph-image.tsx` (`next/og`, built in).

Private areas: `robots: { index: false }` metadata in their layouts **and** disallowed in
`robots.ts`. `/i/[token]` also sends `X-Robots-Tag: noindex`.

Marketing content (blog, features, alternatives) lives as files in `src/content/` and is read at
build time. Format (plain TS objects vs MDX via the official `@next/mdx`) is decided in the
blog feature. Move to a database only when there are hundreds of programmatic pages.

## Theming
All colours come from CSS variables in `src/app/globals.css` (shadcn tokens). When the
design is ready, change tokens there — not hard-coded colours in components. See DESIGN.md.
